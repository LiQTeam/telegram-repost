# مجموعه‌ی تستِ رگرسیونِ رباتِ ری‌پست

این تست‌ها همه‌ی «ثابت‌های منطقیِ» بحرانیِ ربات را (که قبلاً باگ داده بودند) با
اجرای واقعی تأیید می‌کنند تا رگرسیونِ بعدی زود گرفته شود.

## اجرا

```bash
pip install -r requirements.txt      # یا فقط زیرمجموعه‌ی سبک، نگاه کن به نکته‌ی پایین
python3 tests/run_all.py
```

خروجیِ نهایی یا `SUITE RESULT: ALL PASS (N modules)` است یا فهرستِ ماژول‌های
ناموفق (با کدِ خروجِ ۱ — مناسبِ CI). `run_all.py` هم کدِ خروج و هم نشانه‌ی
`FAIL` در خروجیِ هر ماژول را چک می‌کند، چون بعضی فایل‌ها خطا را فقط چاپ
می‌کنند و با کدِ ۰ خارج می‌شوند.

> **دو دسته تست:**
> - تست‌های سبک (`test_formatter`, `test_adfilter`, `test_scraper`,
>   `test_poster`, `test_e2e`, `test_button_colors`) عمداً **بدونِ**
>   torch/cv2/Pillow کار می‌کنند: `_harness.py` یک بسته‌ی سبکِ `bot` می‌سازد که
>   `bot/__init__.py` سنگین را اجرا نمی‌کند، و `_poster_harness.py` ماژول‌های
>   سنگین/دیتابیس را استاب می‌کند.
> - تست‌های یکپارچه (`test_database`, `test_dedup_cache_backup`,
>   `test_v240_modules`, `test_menu_smoke`) روی یک **دیتابیسِ واقعیِ موقت**
>   (پوشه‌ی موقتِ سیستم، نه `data/` پروژه) اجرا می‌شوند و به وابستگی‌های کاملِ
>   `requirements.txt` نیاز دارند (به‌جز torch). هیچ‌کدام به شبکه/توکنِ واقعیِ
>   تلگرام نیاز ندارند.

## فایل‌ها

| فایل | چه چیزی را تست می‌کند |
|---|---|
| `test_formatter.py` | راست‌چینی، idempotency، فوترِ تک‌خطِ‌خالی، توازنِ تگ، دست‌نخوردنِ کانفیگ |
| `test_adfilter.py` | کلیدواژه‌ی سفارشیِ قبل از معافیتِ پروکسی، نرمال‌سازی، مرزِ کلمه، عبورِ خبرِ عادی، ترکیبِ موتورِ قاعده + دو داورِ AI |
| `test_ad_feedback_stats.py` | آمارِ فیدبکِ ادمین به تشخیصِ فیلترِ تبلیغات |
| `test_scraper.py` | آلبومِ واحد، صفحه‌بندیِ کاملِ بازه، کشِ امبد (گذرا در برابر شکستِ واقعی) |
| `test_poster.py` | آلبومِ بی‌متن، سرریزِ کپشن، ویس، شکستِ دانلودِ عکس، تقسیمِ پیامِ بلند، کپشنِ ثابتِ کانفیگ |
| `test_e2e.py` | خروجیِ نهاییِ چند سناریوی واقعی (متنی که به تلگرام می‌رود) |
| `test_button_colors.py` | سیاستِ رنگِ دکمه‌ها + اعتبارِ مقادیرِ `button_config.py` |
| `test_v240_modules.py` | `web_search` (تشخیصِ نوع/پاک‌سازیِ کوئری/چرخشِ ۵ کلید)، `ai_crypto`، سلامتِ `ai_catalog`، یکسانیِ برچسبِ منویِ AI با کاتالوگ |
| `test_database.py` | اسکیما، idempotent بودنِ مهاجرت‌ها، CRUDِ کانال/مقصد/کاربر، تنظیمات، اسلات‌ها، صفِ تایید و claimِ اتمیک، کلیدهای چندتاییِ AI، نگه‌داری و cascade |
| `test_dedup_cache_backup.py` | تشخیصِ تکراری (متن/مدیا/اتمیک)، سقفِ بایتیِ کش و حسابداریِ حجم، رفت‌وبرگشتِ کاملِ بکاپ/بازیابی و سالم‌ماندنِ دیتابیس بعد از بازیابیِ ناموفق |
| `test_menu_smoke.py` | **هر دکمه‌ی اینلاینِ ربات**: تمامِ `callback_data`ها از سورس استخراج و با دیتابیسِ واقعیِ موقت از مسیرِ واقعیِ `_dispatch` اجرا می‌شوند تا هیچ صفحه‌ای خطای زمانِ‌اجرا نداشته باشد |
| `repro_task_gc.py` | نمایشِ الگوی fire-and-forgetِ `create_task` (پس‌زمینه‌ی هاردنینگِ auto_poster) |
| `check_deploy.py` / `rtl_probe.py` | ابزارهای دستیِ بررسیِ استقرار و راست‌چینی (جزوِ سوییتِ خودکار نیستند) |

هر فایل در انتها یا `ALL PASS` چاپ می‌کند یا فهرستِ موارد ناموفق.

## افزودنِ تستِ جدید

فایل را در همین پوشه بساز، در انتها `ALL PASS` یا فهرستِ `FAIL` چاپ کن و با
کدِ ۱ خارج شو، بعد نامش را به `MODULES` در `run_all.py` اضافه کن. اگر به
دیتابیس نیاز داری، **قبل از هر importی از `bot`** متغیرِ `DB_PATH` را روی یک
پوشه‌ی موقت ست کن (نمونه: بالای `test_database.py`) تا `data/` پروژه دست‌نخورده
بماند.
